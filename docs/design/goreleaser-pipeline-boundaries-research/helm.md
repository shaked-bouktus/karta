# Helm: GoReleaser pipeline boundaries

## TL;DR

- C1: Separate Karta's `hack/release` Go program into its own module. Helm has no release-helper module, but it deliberately keeps GoReleaser out of the product module by running `go install` from `/`. Karta should preserve that dependency boundary with a module when the helper is checked-in Go source. It should not copy Helm's unpinned `@latest` install. Makefile (https://github.com/helm/helm/blob/main/Makefile#L156-L167)
- C2: Do not make GoReleaser the owner of ordinary local builds or the main presubmit compile. Helm uses direct `go build` for that path. GoReleaser owns the release cross-build only. Karta can still run a GoReleaser configuration check or snapshot smoke test in presubmit. Makefile (https://github.com/helm/helm/blob/main/Makefile#L63-L70) build-test.yml (https://github.com/helm/helm/blob/main/.github/workflows/build-test.yml#L16-L36) Makefile (https://github.com/helm/helm/blob/main/Makefile#L169-L175)
- C3: Put `act`-only branches and dry-run event shims in a separate workflow. Helm keeps a main-branch canary beside the tag release because both are real publication paths and both are restricted to `helm/helm`. The canary overwrites live canary artifacts. It is not a local workflow emulator path. release.yml (https://github.com/helm/helm/blob/main/.github/workflows/release.yml#L1-L19) release.yml (https://github.com/helm/helm/blob/main/.github/workflows/release.yml#L83-L117)
- C4: Enforce Karta's exact supported release platform set. Do not test only the matrix shape. Helm's exact 12-platform set is part of its build, fetch, installer, and release-note contracts. goreleaser.yaml (https://github.com/helm/helm/blob/main/.goreleaser.yaml#L6-L64) Makefile (https://github.com/helm/helm/blob/main/Makefile#L1-L5) get-helm-4 (https://github.com/helm/helm/blob/main/scripts/get-helm-4#L69-L77) release-notes.sh (https://github.com/helm/helm/blob/main/scripts/release-notes.sh#L80-L97)

## How it works

Helm keeps GoReleaser outside its product dependency graph. The root module declares `helm.sh/helm/v4` and product dependencies. It does not declare GoReleaser. The Makefile explains that tool installation is run outside a directory with a `go.mod` so installation does not alter the product module. go.mod (https://github.com/helm/helm/blob/main/go.mod#L1-L54) Makefile (https://github.com/helm/helm/blob/main/Makefile#L156-L167)

The local build path is direct. `make build` invokes `go build` for `./cmd/helm` with the version linker flags assembled by Make. The broader `make test` path depends on that build, style checks, and unit tests. Makefile (https://github.com/helm/helm/blob/main/Makefile#L34-L70) Makefile (https://github.com/helm/helm/blob/main/Makefile#L79-L105)

Presubmit follows the same direct path. The build workflow checks headers, runs `go mod tidy -diff`, runs coverage, and runs `make build` on Ubuntu. It does not invoke GoReleaser or the cross-build target. Lint is also a separate workflow with an explicit version from `.github/env`. build-test.yml (https://github.com/helm/helm/blob/main/.github/workflows/build-test.yml#L16-L36) golangci-lint.yml (https://github.com/helm/helm/blob/main/.github/workflows/golangci-lint.yml#L10-L27) env (https://github.com/helm/helm/blob/main/.github/env#L1-L2)

The release cross-build is different. `make build-cross` adds static linker flags and calls `goreleaser build --snapshot --clean`. The GoReleaser config compiles `./cmd/helm`, writes binaries under OS and architecture directories, and receives linker flags through the environment. Make then copies the license and README into those directories, creates archives, and computes two checksum formats. Makefile (https://github.com/helm/helm/blob/main/Makefile#L169-L185) goreleaser.yaml (https://github.com/helm/helm/blob/main/.goreleaser.yaml#L3-L67) Makefile (https://github.com/helm/helm/blob/main/Makefile#L195-L212)

The real tag job runs unit coverage, performs the cross-build, packages the result, computes checksums, and uploads it. The main-branch canary repeats the same sequence and uploads with overwrite enabled. Both jobs require the upstream `helm/helm` repository. release.yml (https://github.com/helm/helm/blob/main/.github/workflows/release.yml#L18-L81) release.yml (https://github.com/helm/helm/blob/main/.github/workflows/release.yml#L83-L117)

The GoReleaser matrix starts with three operating systems and eight architectures, then excludes unsupported Darwin and Windows pairs. The result is exactly 12 targets: Darwin amd64 and arm64; Linux 386, amd64, arm, arm64, loong64, ppc64le, riscv64, and s390x; and Windows amd64 and arm64. goreleaser.yaml (https://github.com/helm/helm/blob/main/.goreleaser.yaml#L6-L64)

That exact set appears again in `TARGET_OBJS`, which fetches every archive and both checksum forms. The Helm 4 installer rejects platforms outside the same set. The release-note generator prints download and checksum links for the same set. Makefile (https://github.com/helm/helm/blob/main/Makefile#L1-L5) Makefile (https://github.com/helm/helm/blob/main/Makefile#L187-L193) get-helm-4 (https://github.com/helm/helm/blob/main/scripts/get-helm-4#L69-L77) release-notes.sh (https://github.com/helm/helm/blob/main/scripts/release-notes.sh#L80-L97)

## Relevance to Karta

C1 is a dependency ownership decision, not a directory-style decision. Helm's useful rule is that release-only dependencies must not enter the shipped module graph. A checked-in Karta release helper has compile-time dependencies and tests of its own, so a separate `hack/release/go.mod` is the clearer form of the same boundary. The helper should be run with workspace isolation if Karta's root workspace does not include it. Helm's shell-only release orchestration does not need that module because its Go tool is installed as an external command. Makefile (https://github.com/helm/helm/blob/main/Makefile#L156-L175) go.mod (https://github.com/helm/helm/blob/main/go.mod#L1-L54)

C2 should distinguish a host developer build from a release artifact build. A fast `make` target and the main compile presubmit should call Go directly for Karta's CLI and operator. GoReleaser should own release build IDs, cross-platform expansion, artifact names, and release linker settings. A focused presubmit may validate that GoReleaser can load the config and produce a snapshot, but that is a release-contract test, not the ordinary compile owner. Helm applies this split between `make build`, `build-test.yml`, and `make build-cross`. Makefile (https://github.com/helm/helm/blob/main/Makefile#L63-L70) build-test.yml (https://github.com/helm/helm/blob/main/.github/workflows/build-test.yml#L29-L36) Makefile (https://github.com/helm/helm/blob/main/Makefile#L169-L175)

C3 should distinguish a canary from an emulator fixture. A production canary belongs with the release workflow when it uses the real build and publication path and has an explicit upstream-repository guard. An `act` branch exists to synthesize GitHub events or avoid secrets. It should live in a separate workflow so those accommodations cannot widen the real workflow's triggers, conditions, permissions, or upload behavior. Helm's real workflow exposes only tag creation and main pushes, then narrows both jobs to `helm/helm`. release.yml (https://github.com/helm/helm/blob/main/.github/workflows/release.yml#L1-L20) release.yml (https://github.com/helm/helm/blob/main/.github/workflows/release.yml#L83-L117)

C4 is a user-facing compatibility decision. A test that checks only matrix shape would allow a supported target to disappear while the YAML remains structurally valid. Karta should assert the exact normalized target tuples and any intentional exclusions. It should update that assertion in the same change that updates supported artifacts. Helm shows why: target identities are consumed by packaging, installation, and release documentation, not only by GoReleaser. goreleaser.yaml (https://github.com/helm/helm/blob/main/.goreleaser.yaml#L6-L64) get-helm-4 (https://github.com/helm/helm/blob/main/scripts/get-helm-4#L69-L77) release-notes.sh (https://github.com/helm/helm/blob/main/scripts/release-notes.sh#L80-L97)

## Evidence

- Module boundary: the product module is rooted at `go.mod`, while the Makefile deliberately installs Go tools from `/` to avoid changing that module. go.mod (https://github.com/helm/helm/blob/main/go.mod#L1-L54) Makefile (https://github.com/helm/helm/blob/main/Makefile#L156-L167)
- Local build owner: Make invokes `go build` directly for the Helm CLI. Makefile (https://github.com/helm/helm/blob/main/Makefile#L63-L70)
- Presubmit owner: the main build workflow invokes module checks, coverage, and `make build`, with no release cross-build step. build-test.yml (https://github.com/helm/helm/blob/main/.github/workflows/build-test.yml#L16-L36)
- Release build owner: `build-cross` invokes GoReleaser in snapshot build mode, then Make owns archives and checksums. Makefile (https://github.com/helm/helm/blob/main/Makefile#L169-L212)
- Release workflow boundary: tag release and main canary are in one file because both run real builds and uploads. The jobs are guarded to the upstream repository. release.yml (https://github.com/helm/helm/blob/main/.github/workflows/release.yml#L18-L19) release.yml (https://github.com/helm/helm/blob/main/.github/workflows/release.yml#L83-L117)
- Platform contract: GoReleaser's exclusions normalize to the same 12 targets named by the Helm 4 installer and release notes. goreleaser.yaml (https://github.com/helm/helm/blob/main/.goreleaser.yaml#L9-L64) get-helm-4 (https://github.com/helm/helm/blob/main/scripts/get-helm-4#L69-L77) release-notes.sh (https://github.com/helm/helm/blob/main/scripts/release-notes.sh#L82-L97)
- Test gap: the inspected pull-request build validates one Ubuntu host build. It does not execute `build-cross` or compare the repeated platform lists. build-test.yml (https://github.com/helm/helm/blob/main/.github/workflows/build-test.yml#L16-L36) Makefile (https://github.com/helm/helm/blob/main/Makefile#L169-L175)

## Lessons for Karta

1. Give product code and release-helper code separate dependency lifecycles. A separate module is justified when the release helper is a maintained Go program. go.mod (https://github.com/helm/helm/blob/main/go.mod#L1-L54) Makefile (https://github.com/helm/helm/blob/main/Makefile#L156-L167)
2. Keep ordinary host builds easy to run and debug with direct Go commands. Reserve GoReleaser ownership for release artifacts and release-contract checks. Makefile (https://github.com/helm/helm/blob/main/Makefile#L63-L70) Makefile (https://github.com/helm/helm/blob/main/Makefile#L169-L175)
3. Keep real tag and canary publication close enough to share implementation. Keep `act` event shims outside that trust boundary. release.yml (https://github.com/helm/helm/blob/main/.github/workflows/release.yml#L1-L19) release.yml (https://github.com/helm/helm/blob/main/.github/workflows/release.yml#L83-L117)
4. Treat platform removal as an intentional compatibility change. Test exact tuples, archive formats, and build IDs. goreleaser.yaml (https://github.com/helm/helm/blob/main/.goreleaser.yaml#L6-L64) Makefile (https://github.com/helm/helm/blob/main/Makefile#L1-L5)
5. Derive installers and release notes from one normalized platform source when possible. Helm's consumers show all the places that must agree. Makefile (https://github.com/helm/helm/blob/main/Makefile#L1-L5) get-helm-4 (https://github.com/helm/helm/blob/main/scripts/get-helm-4#L69-L77) release-notes.sh (https://github.com/helm/helm/blob/main/scripts/release-notes.sh#L80-L97)

## What NOT to copy

- Do not install GoReleaser with `@latest`. Helm isolates the dependency but does not make the tool version reproducible. Pin Karta's tool version in its release-tool boundary. Makefile (https://github.com/helm/helm/blob/main/Makefile#L156-L167)
- Do not duplicate tag and canary job bodies. Helm repeats checkout, Go setup, tests, cross-build, packaging, checksums, and upload configuration. Karta should share those steps through a reusable workflow, composite action, or repository script. release.yml (https://github.com/helm/helm/blob/main/.github/workflows/release.yml#L18-L81) release.yml (https://github.com/helm/helm/blob/main/.github/workflows/release.yml#L83-L117)
- Do not add fake `act` branches to production release conditions. Helm's branch path is a real canary with a real upload and an upstream-repository guard. release.yml (https://github.com/helm/helm/blob/main/.github/workflows/release.yml#L83-L117)
- Do not copy the same platform list into several consumers without an exact consistency test or generation step. Helm repeats the set in GoReleaser, Make, the installer, and release notes. goreleaser.yaml (https://github.com/helm/helm/blob/main/.goreleaser.yaml#L6-L64) Makefile (https://github.com/helm/helm/blob/main/Makefile#L1-L5) get-helm-4 (https://github.com/helm/helm/blob/main/scripts/get-helm-4#L69-L77) release-notes.sh (https://github.com/helm/helm/blob/main/scripts/release-notes.sh#L80-L97)
- Do not treat one Linux host build as proof that the release matrix is healthy. Helm's pull-request build does not execute the cross-build path. Karta should add a focused release-contract presubmit. build-test.yml (https://github.com/helm/helm/blob/main/.github/workflows/build-test.yml#L16-L36) Makefile (https://github.com/helm/helm/blob/main/Makefile#L169-L175)
